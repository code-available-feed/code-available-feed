# code-available-feed

A weekly Atom feed of arxiv articles that mention a code, data, or demo URL in their
`arxiv:comment` field, generated from the arxiv API without scraping.

## Value Proposal

The arxiv API does not expose a flag indicating whether an article has associated code.
However, articles that provide code, data, or demo sites list one or more
`https://` URLs in their `arxiv:comment` field (visible for example on the arxiv
listing page at `https://arxiv.org/list/cs.AI/current`).
Filtering on the presence of any such URL requires only the comment field, no PDF
download and no abstract parsing.

The subset of articles associated with code is useful because:
- Code availability suggests reproducibility may have been considered.
- The linked URLs let a reader assess scope before committing to reading the article.
- arxiv's own web feeds cover all articles with no filtering with counts of hundreds per day.
- paperswithcode.com, which was the source of a filtered RSS feed provided by a 3rd party
  https://github.com/ml-feeds/pwc-feeds project, is maintained by https://huggingface.co/
  and no longer exposes the necessary data.

This project generates one Atom 1.0 feed file per ISO calendar week.
Each article contains the title, authors, published date, the arxiv abstract URL, the abstract text, and the comment.
The code detection algorithm scans the article text, excluding the `References` section, for common code-hosting domains, such as github.com, gitlab.com, and huggingface.co.
This maximizes [recall](https://en.wikipedia.org/wiki/Precision_and_recall) at the cost of generating false positives.
The pdfs of the articles are downloaded, scanned on the fly, and discarded.

A fork of the repository can serve a different arxiv category by setting the GitHub
repository variable (`ARXIV_CATEGORY_ID`) without changing the project code.
Additional variable (`ARXIV_CATEGORY_STRICT`), set by default to `false` controls
whether all categories of the article are considered for inclusion in the feed,
or only the primary category is considered.

## Functional Requirements

| ID | Feature | Designer's Note |
|----|---------|-----------------|
| FR-001 | A GitHub Actions workflow runs on a daily schedule; it fetches all articles submitted to the configured arxiv category during the rolling window `[today - ARXIV_MAX_BACKFILL_DAYS, today]` via the arxiv API at `https://export.arxiv.org/api/query`; the query uses `search_query=cat:{ARXIV_CATEGORY_ID}+AND+submittedDate:[YYYYMMDD0000+TO+YYYYMMDD2359]&sortBy=submittedDate&sortOrder=descending` with `today - ARXIV_MAX_BACKFILL_DAYS` and `today` as the YYYYMMDD date bounds; `max_results` is set to `ARXIV_MAX_RESULTS` and the `start` parameter is incremented in steps of `max_results` until the returned count is less than the requested count, to paginate categories whose weekly submission count exceeds one page; if the first request (`start=0`) returns a 200 response with zero articles, the pipeline logs a message and exits with code 0 without writing any file (valid empty result, e.g. a quiet period for a small category); subsequent pagination pages (`start>0`) returning zero articles are treated as a normal end-of-results signal and do not trigger a failure; the rolling window replaces the former ISO week bounds to recover articles submitted after Thursday 14:00 ET, which the arXiv announcement schedule (source: `https://info.arxiv.org/help/availability.html`) delays until after the ISO week boundary; with the default `ARXIV_MAX_BACKFILL_DAYS=8`, Monday's run covers the full prior ISO week plus one extra day | The arxiv API supports date range filtering via `submittedDate` as documented at `https://info.arxiv.org/help/api/user-manual.html`; the maximum `max_results` is 30,000; small page sizes avoid HTTP 429 rate limiting from the arxiv API (live testing showed 2000 triggers HTTP 429 consistently, but even 50 also tends to trigger HTTP 429 sometimes); daily re-fetching the rolling window is idempotent; `sortBy=submittedDate&sortOrder=descending` is required for stable pagination: without an explicit sort directive the API may return overlapping or missing articles across successive pages; the end bound `YYYYMMDD2359` covers only up to 23:59:00 and technically misses articles submitted in the last 59 seconds of the end date — this gap is accepted as harmless because arxiv applies a daily submission cutoff at 14:00 US Eastern and articles become visible in the API around 00:00 UTC the following day, so no real submission falls in the 23:59:01-23:59:59 window; cs.AI has approximately 1000 articles per week (4,000 per month / 4.3 weeks), so multiple paginated requests are needed per run for that category; a zero-result response on the first page typically signals an API issue (except in low volume categories) rather than a genuine absence of articles; a zero result on a subsequent pagination page is expected when the total article count is an exact multiple of `max_results`; `ARXIV_API_BASE_URL` overrides the API base URL (default `https://export.arxiv.org`) and exists solely for test injection — setting it to a local fixture server prevents tests from hitting the live API; `PIPELINE_TODAY` overrides the current UTC date used to compute the rolling window bounds (default: actual current UTC date) and exists solely for test injection — it must be in `YYYY-MM-DD` format |
| FR-002 | An article is included in the feed if and only if two conditions hold: (1) the primary-category condition, controlled by `ARXIV_CATEGORY_STRICT`: when `false` (the default) every article returned by the API query is eligible regardless of its `<arxiv:primary_category>`; when `true` the article's `<arxiv:primary_category term="..."/>` lowercased must match `ARXIV_CATEGORY_ID` lowercased (both values are normalized to lowercase before comparison, consistent with the project-wide lowercasing convention); (2) a code-availability URL was found by the cascading search, which checks three sources in order and stops at the first match: (a) comment — any `https://` URL in `<arxiv:comment>` qualifies regardless of domain; (b) abstract — only URLs on accepted domains (`github.com`, `gitlab.com`, `huggingface.co`, `*.github.io`) in `<summary>` qualify, matched via both `https://` scheme regex and bare domain regex (e.g. `github.com/user/repo` without scheme); (c) PDF body — accepted-domain URLs extracted from the PDF up to the References section (see FR-016); the cascade outcome is recorded per article as `repo_found_in` (`"comment"`, `"abstract"`, `"pdf"`, or `""`) and `repo_urls` (the URLs that caused inclusion) | The arxiv listing page at e.g. `https://arxiv.org/list/cs.AI/current` shows all articles cross-listed to cs.AI, not only those with cs.AI as primary; `ARXIV_CATEGORY_STRICT=false` (default) replicates that behaviour; `ARXIV_CATEGORY_STRICT=true` narrows to articles whose primary focus is the configured category — the live API confirmed that a `cat:cs.AI` query returns articles with for example `primary_category=cs.CV`; the comment rule accepts any `https://` URL because authors use the comment field to post project website links that do not match the accepted domain set but still indicate code availability; abstract and PDF text is free-form and may contain unrelated links (journal DOIs, institutional pages), so only accepted-domain URLs are matched there; the bare domain regex catches URLs rendered without `https://` scheme (e.g. when LaTeX uses `\href{url}{icon}` and the text layer contains only the domain and path); tightening the comment URL filtering to accepted domains only is deferred (see Deferred Features) |
| FR-003 | For each included article the pipeline records: the article title (from `<title>`), all author names (from `<author><name>` elements, in document order), the primary category (from `<arxiv:primary_category term="..."/>`), the arxiv abstract page URL (from `<link rel="alternate" type="text/html">`, e.g. `https://arxiv.org/abs/0000.00000v1`; this is the main article page on arxiv, not the PDF and not the HTML-rendered article at `arxiv.org/html/...`), the first publication date (from `<published>`, which the arxiv API defines as "the date the first version was submitted and processed", in RFC 3339 format), the latest version date (from `<updated>`, which the arxiv API defines as "the date the retrieved version was submitted and processed", in RFC 3339 format; identical to `<published>` for v1 articles), the abstract text (from `<summary>`), and all `https://` URLs extracted from the comment in order of appearance with trailing punctuation characters from the set `.,;:)]>` stripped from each URL | The abstract page URL from `<link rel="alternate" type="text/html">` is used in preference to `<id>` because `<id>` uses `http://` while the link element already carries `https://`; the PDF link (`rel="related" type="application/pdf"`) is discarded; no full category list |
| FR-004 | The pipeline generates an Atom 1.0 feed (RFC 4287) from the collected articles; articles are sorted by first arxiv publication date (`<published>`) descending (newest first); a same-week revision does not change an article's position; each `<entry>` contains: `<title>` (article title prefixed with the primary category in brackets, e.g. `[cs.CV] Entity-Consistent Video Generation`; the prefix is always present in the item title regardless of whether the primary category matches `ARXIV_CATEGORY_ID`), one `<author><name>...</name></author>` element per author in document order, `<category term="..." scheme="http://arxiv.org/schemas/atom"/>` (the primary category, e.g. `cs.AI`), `<id>` (arxiv abstract page URL), `<link href="..." rel="alternate" type="text/html"/>` (arxiv abstract page URL), `<published>` (first arxiv publication date from arxiv `<published>`, RFC 3339; optional per RFC 4287, stays static across revisions), `<updated>` (latest revision date from arxiv `<updated>`, RFC 3339; required per RFC 4287; equals `<published>` for v1 articles), and `<content type="html">` (structured HTML block with three sections, each section headed by an `<h3>` element followed by a `<p>` element: `<h3>Authors:</h3><p>` author credit `</p>` — the name of the first author followed by ` et al.` when there are 3 or more authors in total, or all author names joined by `, ` when there are 1 or 2; `<h3>Abstract:</h3><p>` abstract text `</p>` from the API (`<summary>`); `<h3>Comments:</h3><p>` verbatim `<arxiv:comment>` text `</p>`; all user-supplied text in the content block is HTML-escaped with `html.escape()` before being XML-serialised, so that feed readers rendering `type="html"` in a browser display correct spacing and do not misinterpret `&` or `<` in abstracts or comments as HTML markup; the `<author>` Atom elements in the entry continue to list every author in document order and are unaffected by the `et al.` presentation rule); the top-level `<feed><title>` is `"{ARXIV_CATEGORY_ID} strict={ARXIV_CATEGORY_STRICT} {GITHUB_REPOSITORY}"` where `GITHUB_REPOSITORY` is the `owner/repo` value set by GitHub Actions (e.g. `"cs.AI strict=false owner/code-available-feed"`); the top-level `<feed><updated>` is the `<published>` date of the first article (the one with the newest `<published>` date in the `<published>`-descending list) | RFC 4287 defines `<published>` as "an instant in time associated with an event early in the life cycle of the entry" (static) and `<updated>` as "the most recent instant in time when an entry was modified in a way the publisher considers significant"; the natural mapping is arxiv `<published>` → Atom `<published>` and arxiv `<updated>` → Atom `<updated>`; if an article is revised within the same week, the `<entry>`'s `<updated>` will change on the next daily regeneration and some feed readers may re-show the article — this is correct behaviour since the article content changed; if an article is revised within the same week the API may return a `v2` URL, which feed readers treat as a new article — this is intentional because a new version may contain changes that warrant a fresh read; the apparent duplicate disappears when the week rolls over and same-week revisions are rare; `<feed><updated>` uses the newest article's `<published>` rather than the maximum `<updated>` across articles or the pipeline execution timestamp because this value is deterministic across repeated runs with the same input data, which is required by NFR-005's byte-for-byte idempotency guarantee; using the pipeline run time would cause the output to differ on every run even when no data changed, defeating the no-commit guard in FR-006; using the maximum `<updated>` would also be deterministic but would shift the feed-level timestamp on revision-only days when no new articles appeared, which is less informative to subscribers |
| FR-005 | The current feed is stored at `docs/arxiv/{category}/atom.xml`, where `{category}` is the value of `ARXIV_CATEGORY_ID` lowercased (e.g. `cs.AI` becomes `docs/arxiv/cs.ai/atom.xml`); the lowercasing is a project-wide convention: the case-sensitive arxiv category ID is always converted to lowercase for all file paths, URLs, and internal comparisons to avoid platform-dependent case sensitivity issues; at the start of each workflow run, before any early-exit path (including 0 articles returned or 0 articles passing the filter), the script parses the ISO week number of the newest `<entry><published>` date in the existing `docs/arxiv/{category}/atom.xml` (if the file exists) and compares it to the ISO week number of today; if they differ, the existing file is copied to `docs/arxiv/{category}/archive/YYYY-WNN/atom.xml` (e.g. `docs/arxiv/cs.ai/archive/2025-W03/atom.xml`) before the file is overwritten with the new data; no archive step is performed on the very first run; a write-once guard prevents overwriting an existing archive file: if `archive/YYYY-WNN/atom.xml` already exists, the archive step is a no-op (multiple daily runs can all attempt archiving without creating duplicates) | The `archive/YYYY-WNN` path uses the ISO 8601 week notation; the `arxiv` path segment identifies the data source and permits future addition of other sources under the same repository; lowercasing the category ID is a deliberate choice to avoid case-sensitivity issues on case-insensitive filesystems (macOS, Windows) and in URL routing; under the orphan-branch deployment model the prior `docs/arxiv/` state is restored from the `gh-pages` branch before the pipeline runs, so that `archive_prior_week_feed` has access to the previously deployed `atom.xml` and can detect week rollovers; archiving runs unconditionally before any early-exit path so that week boundaries are not missed when the API returns zero articles or all articles are filtered out; the write-once guard is needed because once the archive call is moved before the API fetch, subsequent runs on the same day would see the prior-week entries still in atom.xml (if no new data was written) and attempt to re-archive |
| FR-006 | The `pipeline_feed` workflow generates `docs/arxiv/{category}/atom.xml` and any newly created archive file, then uploads the `docs/arxiv/` directory tree as a GitHub Actions artifact named `arxiv-feed` (7-day retention); the `deploy_orphan` workflow downloads this artifact and force-pushes `docs/arxiv/` to the `gh-pages` orphan branch so that GitHub Pages serves the updated feed; the pipeline script constructs a commit message by counting `<entry>` elements in the generated atom.xml and reading the ISO week of the newest `<entry><published>` date, with format `Update YYYY-WNN feed (N articles)` (singular `1 article` when N is 1), and the same string is used both as a stdout log line from the pipeline and as the commit message subject of the gh-pages orphan commit produced by `deploy_orphan.sh`; if the generated `atom.xml` is byte-for-byte identical to the local file at `docs/arxiv/{category}/atom.xml`, which the workflow restores from the `gh-pages` branch before the pipeline runs, the pipeline prints `no change: feed unchanged` to stdout instead and `deploy_orphan` is still invoked (the force-push of an identical tree is a no-op in content terms but produces a fresh orphan commit); the `pipeline_feed` workflow has `contents: read` and `actions: write` permissions; the `deploy_orphan` workflow has `contents: write` and `actions: read` permissions | Orphan-branch deployment keeps feed files off `main`; `main` stays clean with only code and configuration; force-pushing a fresh orphan commit on each deployment prevents unbounded growth of `gh-pages` git history while preserving the full feed archive in the branch content; GitHub Actions artifacts serve only as the handoff mechanism between `pipeline_feed` and `deploy_orphan` within the same workflow-run chain, not as the long-term store; the artifact retention also functions as the de-facto rollback window: a prior artifact can be replayed via `workflow_dispatch` on `deploy_orphan` to restore a known-good feed; the `gh-pages` branch is the permanent store because git branch content has no automatic expiry; the `pipeline_feed` workflow restores the prior `docs/arxiv/` state from `gh-pages` before running the pipeline so that `archive_prior_week_feed` can detect week rollovers and the no-change guard can compare against the previously deployed content; the commit-message string serves two purposes (stdout log line and gh-pages orphan commit subject), reconstructed in `deploy_orphan.sh` from the generated `atom.xml` via the same `src/pipeline_feed.py` function (`build_commit_message`) used by the pipeline so the two uses cannot drift; constructing the message in a Python module rather than in the workflow YAML keeps it locally testable; a zero-article feed never reaches this stage because FR-011 exits non-zero before any commit when all articles are filtered out; when `GITHUB_TOKEN` is unset (local invocations), `deploy_orphan.sh` asserts that the local repository's `origin` URL matches `GITHUB_REPOSITORY` to prevent accidentally deploying from a wrong checkout |
| FR-007 | GitHub Pages is configured to serve the `docs/` directory from the `gh-pages` orphan branch; the feed URL for account `{user}` with repository named `{repo}` is `https://{user}.github.io/{repo}/arxiv/{category}/atom.xml` (e.g. `https://owner.github.io/code-available-feed/arxiv/cs.ai/atom.xml`) | Static file serving via GitHub Pages requires no server infrastructure; the gh-pages branch is force-pushed on each deployment, keeping git history on main clean; the `arxiv` path segment identifies the data source; the category subdirectory makes the feed URL self-describing; a fork that changes `ARXIV_CATEGORY_ID` to `cs.CV` gets its feed at `.../arxiv/cs.cv/atom.xml` with no code change |
| FR-008 | Two GitHub Actions repository variables control filtering: `ARXIV_CATEGORY_ID` sets the arxiv category identifier (default `cs.AI`; the workflow `env` block supplies this default so the repository works without any variable configuration); `ARXIV_CATEGORY_STRICT` sets the primary-category filter (default `false`; when `true` only articles whose `<arxiv:primary_category>` matches `ARXIV_CATEGORY_ID` are included); two additional variables control pipeline error handling and feed staleness alerting: `ARXIV_CONTINUE_ON_API_ERROR` (default `false`; `ARXIV_CATEGORY_STRICT` is a string variable since GitHub Actions repository variables are always strings; the pipeline lowercases the value and compares it against the string `true` — only the value `true` (any casing: `true`, `True`, `TRUE`) enables strict mode; `ARXIV_MAX_STALENESS_DAYS` is a string that must parse as `-1` (disabled) or a positive integer, validated at check time by `run_staleness_check` in `src/pipeline_feed.py` |
| FR-009 | The feed `<id>` and `<link rel="self" href="..."/>` are set to the canonical GitHub Pages URL of the feed; the pipeline script constructs this URL directly from the `GITHUB_REPOSITORY` environment variable (format `owner/repo`, always set by GitHub Actions regardless of trigger type) as `https://{owner}.github.io/{repo}/arxiv/{category}/atom.xml` where `{owner}` and `{repo}` are split from `GITHUB_REPOSITORY` and `{category}` is `ARXIV_CATEGORY_ID` lowercased; for local testing `GITHUB_REPOSITORY` is set as an environment variable (e.g. `GITHUB_REPOSITORY=owner/code-available-feed`); the `<entry><id>` of each article is the versioned arxiv abstract page URL as returned by the API (e.g. `https://arxiv.org/abs/0000.00000v1`) | `github.event.repository.name` is empty for `schedule`-triggered workflows because `github.event` is `{}` on schedule; `GITHUB_REPOSITORY` (format `owner/repo`) is always set by GitHub Actions regardless of trigger type; having the pipeline construct the URL itself keeps the logic in one place and makes it testable locally without a workflow; a stable `<feed><id>` prevents feed readers from treating the same feed as a new subscription after a fork renames the repository |
| FR-010 | A Docker-based validation step runs unconditionally against the file on disk after the pipeline exits, regardless of whether the byte-comparison guard wrote a new file; a single container starts `python -m http.server` in the background to serve `docs/` on a local port, then runs newsboat in non-interactive mode (`newsboat --url-file <tmpfile> --execute reload`) once for the current week's feed URL and, if an archive exists, once for the most recent archived feed URL (the lexicographically latest `YYYY-WNN` directory if any archive exists, whether created during the current run or a prior run); each invocation uses a separate single-entry temporary URL file; the workflow step fails and no commit is made if either newsboat invocation exits with a non-zero code | A parse-only XML well-formedness pre-check (`scripts/check_atom_xml.sh`) runs before the pipeline to catch a corrupt restored feed early; newsboat validation then runs unconditionally on the file on disk after the pipeline writes (or leaves unchanged) the atom.xml, so a feed with invalid XML is detected even when it is byte-identical to the prior version; validating the preceding week's archived feed detects regressions in the Atom XML format across week boundaries; newsboat validates both HTTP serving and Atom XML well-formedness; separate per-URL invocations give a distinct exit code per URL so the failing feed can be identified from the workflow log; a single container is sufficient since newsboat is a lightweight client that does not need isolation from the server; newsboat is installed via `Dockerfile.server` using `apt-get install -y --no-install-recommends newsboat`; on the very first run no archive exists and newsboat validates only the current week's feed — single-file validation is accepted as sufficient for the first run since the two-file path is exercised from the second week onward |
| FR-011 | If the first arxiv API request (`start=0`) returns a non-200 HTTP status, the pipeline retries it up to 3 times with exponential backoff (N × RETRY_BACKOFF_BASE_SECONDS seconds before the N-th retry; with the default RETRY_BACKOFF_BASE_SECONDS=60 the delays are 60 s, 120 s, and 180 s before retries 1 through 3); if all retries fail, the pipeline exits with a non-zero exit code and no commit is made; a non-200 HTTP status on any subsequent pagination request (`start>0`) causes the pipeline to exit immediately with a non-zero exit code without retrying; if the inclusion filter eliminates all articles returned by the API (i.e. zero articles pass the filter), the pipeline logs a message and exits with code 0 without writing any file; if `GITHUB_REPOSITORY` is not set the pipeline exits with a non-zero exit code and no commit is made | Transient API errors (503, timeouts) are common for `export.arxiv.org`, and rate-limiting HTTP 429 even more common; 3 retries with exponential backoff handle most transient failures; retries are limited to the first request because a failure on a subsequent pagination page indicates the session has already succeeded for earlier pages and the error is unlikely to be a simple transient burst — exiting immediately avoids assembling and committing a partial result; failing loudly when filtering eliminates all articles and prevents silently publishing an empty feed; `RETRY_BACKOFF_BASE_SECONDS` sets the base sleep duration for exponential backoff in seconds (default `60`; the N-th retry sleeps `N × RETRY_BACKOFF_BASE_SECONDS` seconds) |

when the pipeline fails gracefully across a week boundary, `atom.xml` retains the last successfully-written content and its newest published date ages past 7, 14, or more days until the API recovers, making the staleness check correct for any gap duration; `archive_prior_week_feed` now runs unconditionally before any early-exit path (FR-005 archive fix), so archiving is not affected by API failures; `ARXIV_MAX_STALENESS_DAYS` defaults to `-1` (disabled) in `scripts/check_feed_staleness.sh` so a bare local invocation of the script is a no-op |
| FR-016 | The pipeline extracts accepted-domain URLs from the PDF body (up to the References section) as the third source in the cascade (after comment and abstract, see FR-002); three extraction layers are applied per page in order: (1) link annotation extraction via `pypdf`'s `page.annotations` (primary, most reliable: returns full `https://` URIs from PDF hyperlink metadata); (2) text `https://\S+` regex on `page.extract_text()` (fallback 1: catches URLs visible as text with scheme); (3) text bare domain regex `(?:domain1\|domain2\|...)/\S+` on the same extracted text (fallback 2: catches URLs without `https://` scheme, e.g. when LaTeX renders `\href{url}{icon}`); scanning stops before the References section: if the page text contains a standalone "References" or "REFERENCES" line, all subsequent pages are skipped; all URLs from all three layers are collected, deduplicated, filtered to the accepted domain set, sorted, and returned; `enrich_from_pdf` downloads the PDF from `https://export.arxiv.org/pdf/{arxiv_id}`, calls `extract_pdf_repo_urls`, and wraps the entire body in `try/except Exception` so any failure (network, HTTP, pypdf parse error) is logged at ERROR level and returns `None` (the caller excludes `None` results so failed articles are retried on the next run); PDF enrichment runs in a `ThreadPoolExecutor` with `max_workers=3`; each worker sleeps 5 seconds before its request (NFR-002); PDF failures are always non-fatal regardless of `ARXIV_CONTINUE_ON_API_ERROR` | Three extraction layers are needed because no single method works for all cases: testing on real arxiv PDFs showed that `https://\S+` regex fails when LaTeX renders a URL via `\href{url}{icon}` with no scheme in the visible text; annotation extraction handles this case; the bare domain regex handles it via the domain string in the text; the References stop-guard prevents false positives from cited URLs (e.g. a cited dataset URL on page 10 is not the paper's own code); `pypdf` is installed via `apt-get install python3-pypdf` (see NFR-001 amendment); `concurrent.futures` is in the standard library so NFR-001 is unaffected; worst-case burst is 3 concurrent requests, under the arXiv guideline of 4 per second documented at `https://info.arxiv.org/help/bulk_data.html` |
| FR-017 | The pipeline persists the cascade outcome for each article in a `<code-available-feed:processed>` extension element inside `docs/arxiv/{category}/atom.xml`; each child element `<code-available-feed:article>` has attributes `url` (the article's `abstract_url`), `updated` (the article's `updated` date), `repo_found_in` (`"comment"`, `"abstract"`, `"pdf"`, or `""` meaning cascade ran and found nothing), and `repo_urls` (space-joined sorted URLs, or `""` if none); child elements are sorted by `url` for NFR-005 determinism; on each run, `load_processed` parses the element and retains only entries whose `updated` date falls within `[today - ARXIV_MAX_BACKFILL_DAYS, today]`; previously processed articles with non-empty `repo_found_in` are included directly without re-running the cascade; previously processed articles with empty `repo_found_in` are excluded directly; new articles not in the processed dict are enriched via the cascade; `build_feed` writes the updated processed dict as a feed-level extension element; when `filtered` is empty (no code articles this run), `write_processed_element` updates the existing atom.xml in place without touching its `<entry>` elements so the processed state is preserved for the next run; `write_processed_element` does nothing when atom.xml does not exist; the namespace URI is `tag:code-available-feed.github.io,2026:atom-extensions`, registered as prefix `code-available-feed` | The processed dict prevents redundant PDF downloads on repeated runs: for cs.AI (~900 articles/week without a comment URL), each run would otherwise re-download and re-scan all PDFs from prior runs; arXiv does not allow in-place metadata edits after announcement (source: `https://info.arxiv.org/help/replace.html`), so a processed entry cannot become stale due to a metadata change; any change requires a new version (v2, v3) with a new `abstract_url` key, causing the cascade to run fresh; the only exceptions are journal reference, DOI, and report number, none of which affect code-URL detection; `write_processed_element` uses `ET.indent(processed_element, space="  ", level=1)` on the modified sub-element only because the processed element sits at depth 1 inside `<feed>` and a full-tree indent pass would corrupt whitespace; feed readers ignore the extension element (unknown namespace) |

## Default Values

The following variables have different defaults at each layer.
The workflow default is the effective default for scheduled CI runs.
The shell default applies when scripts are invoked directly without the workflow's `env` block.
The Python default applies when the script is invoked without setting the environment variable at all.

| Variable | Workflow default | Shell default | Python default |
|----------|-----------------|---------------|----------------|
| `ARXIV_CONTINUE_ON_API_ERROR` | `true` | `''` (treated as `false`) | `''` (treated as `false`) |
| `ARXIV_MAX_BACKFILL_DAYS` | `8` | `8` | `8` |
| `ARXIV_MAX_STALENESS_DAYS` | `10` | `-1` (disabled) | `-1` (disabled) |

The discrepancy is intentional: in CI the fail-safe defaults prevent noisy failure notifications from transient API outages; locally a bare script invocation takes the conservative path that matches the documented requirement contract.

## Expected Characteristics

The weekly Atom XML file for cs.AI is expected to contain approximately 100 articles (1 in 10 of ~1000 articles per week have a `https://` URL in their comment).
Based on real pipeline output from mid 2026, each article occupies approximately 3 KB (title, authors, abstract, and structured content block).
At that rate, 100 articles per week occupy approximately 300 KB; monthly approximately 1 MB; yearly approximately 15 MB per category.
The 1-in-10 ratio is a best estimate based on observation of the cs.AI arxiv listing page.

## Technical Choices

**Data source:**
The arxiv API at `https://export.arxiv.org/api/query` returns an Atom feed containing
`<arxiv:comment>` per article when a comment is present.
The endpoint redirects `http://` to `https://`; the pipeline must use `https://` directly.
Querying by `cat:{category} AND submittedDate:[...]` retrieves all articles for the
configured category and week without fetching PDFs or abstract pages.
The API does not support field selection: every response includes the full
`<summary>` (abstract), all `<author>` elements, PDF link, and category list regardless
of what the caller needs; the pipeline discards everything except title, authors, primary category, link, published, updated,
and comment.
Live call confirmed 2026-05-16: `https://export.arxiv.org/api/query?search_query=cat:cs.AI&start=0&max_results=1&sortBy=submittedDate&sortOrder=descending`
returns 3.1 KB for one article with all fields present.
The API does not expose a flag or filter for articles with associated code repositories;
this was confirmed both from the documentation at `https://info.arxiv.org/help/api/user-manual.html`
and from the live response.
Documentation at `https://info.arxiv.org/help/api/user-manual.html`.

**Comment URL extraction:**
`re.findall(r'https://\S+', comment)` returns a list of all non-overlapping `https://`
URL matches in the comment string; `\S+` stops at whitespace, so two URLs separated
by any whitespace or text are captured independently — for example the comment
`"Code: https://code.example.com/foo/bar demo: https://demo.example.com/"` yields both URLs.
A second pass strips trailing punctuation characters (`.,;:)]>`) from each match to
handle constructs like `available at https://code.example.com/foo/bar.` without removing
path separators or query-string characters.

**No database:**
The only output artifact is an Atom XML file.
A database would add schema design, migration handling, and artifact caching
across workflow runs, all with no benefit when the output is a static text file.

**Fork configurability:**
GitHub Actions repository variables (`${{ vars.ARXIV_CATEGORY_ID }}`
and `${{ vars.ARXIV_CATEGORY_STRICT }}`) are set per repository and not inherited by forks.
A fork sets `ARXIV_CATEGORY_ID` to the target category in its own Settings page.
The workflow falls back to `cs.AI` when the variable is absent.
The default value of `ARXIV_CATEGORY_STRICT`, if not set, is `false`.
No code change is needed in the fork.

**Docker for validation:**
`Dockerfile.server` builds from `debian:trixie-slim` and installs newsboat
(feed validation), python (runtime), behave and mypy (test toolchain), and
a small set of OS utilities for HTTPS and diagnostics, all via `apt-get`.
The compose `server` service builds from `Dockerfile.server`, overrides the
default `CMD` with `python -m http.server 8000 --bind 0.0.0.0`, and mounts
the repository root at `/app`.
Newsboat and the BDD test runner (behave) run inside the same container so
the validation environment is identical between local development and CI.

**GitHub Actions schedule:**
The workflow runs several times a day.
arxiv articles submitted the previous US business day appear on the API after 00:00 UTC,
but the arXiv API often returns HTTP 503 or 429, so the workflow is triggered several times daily,
hoping it will eventually succeed.

**Failed GitHub Actions notifications:**
The arXiv API tends to fail often with HTTP 503 or 429, so two variables are introduced to base
notifications on a missing feed items instead of the arXiv API errors.
`ARXIV_CONTINUE_ON_API_ERROR` set to true in the `pipeline_feed.yml` will mark the pipeline as succeeded
even if the arXiv API errors are present, and `ARXIV_MAX_STALENESS_DAYS`
will fail the pipeline when no new feed item appears for more than the configured number of days.

## Deferred Features

| Feature | Reason for Deferral |
|---------|---------------------|
| OPML 1.0 subscription list in the directory repo | A static `feeds.opml` file in the central directory repo (`code-available-feed/code-available-feed`), served via GitHub Pages along `atom.xml` and updated via pull requests; spec: `https://opml.org/spec2.opml` |
| Domain allowlist for comment URL filtering | Abstract and PDF filtering already uses an accepted-domain set (FR-002), but comment URLs still accept any `https://` URL; restricting comments to the same accepted-domain set would reduce false positives from journal or institution URLs but may lose project-website links that authors place in comments; deferred until the false-positive rate is measured on real data |
| RelaxNG schema validation of generated Atom XML | `xmllint --relaxng` with the RFC 4287 schema would catch missing required Atom fields that Python's `xml.etree.ElementTree` and newsboat (libxml2 recovery mode) both silently accept; deferred because embedding the RFC 4287 XML RelaxNG schema requires either converting the compact `.rnc` from Appendix B (needs `trang` or `rnc2rng`, neither in the current apt dependencies) or sourcing a pre-converted `.rng` from a third party, adding supply-chain risk for a validation-only file |
| `workflow_dispatch` with custom date range | Basic manual trigger is implemented (FR-012) but without date range parameters; running the workflow manually for a past week would allow backfilling gaps caused by runner outages; the custom date range input is deferred as it adds workflow complexity not needed for normal operation |

## Abandoned Ideas

| Idea | Reason for Abandonment |
|------|------------------------|
| Downloading PDFs to detect code links (full PDF processing) | The original concern was downloading 500-1000 PDFs per week requiring gigabytes of temporary storage and hours of processing; FR-016 implements a bounded variant: only the paper body up to the References section is scanned (not the full PDF), using `pypdf` for in-memory extraction (no temporary storage), with a `processed` dict (FR-017) preventing redundant downloads on subsequent runs; only articles not already found via comment or abstract (FR-002 cascade) reach the PDF step, so the steady-state cost is bounded to new articles from the latest day |
| Scraping the arxiv listing page HTML | Scraping is fragile and against the arxiv terms of use; the API provides the same comment field in structured form |
| Using the paperswithcode API or data export | paperswithcode.com shut down its public API and RSS feed in 2025 and the project cannot depend on an unavailable third-party service |
| Git LFS for archived weekly files | Atom XML is plain text compressing well under standard git; with the estimated 100 articles with code per week the yearly storage space is 15 MB and there is no need for LFS |
| Multiple categories in one repository | One category per fork is sufficient; supporting multiple categories in one repository requires either multiple feed files (complicating the archive logic) or a merged feed (losing per-category subscriptions) |
| Direct commits to `main` for feed updates | Committing `docs/arxiv/atom.xml` to `main` mixed generated content with source code and grew `main`'s git history unboundedly; replaced by the orphan-branch model which keeps `main` clean and lets the deploy step force-push without accumulating history |
| Index feed listing all archived weeks | A subscribable index of past weeks would help readers discover older archives |
